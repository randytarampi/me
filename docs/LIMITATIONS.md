# Limitations

- Every workspace package now declares an explicit `"type": "module"` field, including `packages/service` (the last holdout - see below) - full ESM, as originally asked about. Previously most packages had no `"type"` field at all, silently defaulting to CommonJS per Node's resolution algorithm - this is what broke `job-application`/`jsonresume-theme`/`letter`/`resume`'s `server.js` (`ReferenceError: exports is not defined in ES module scope`), since Node's ESM-syntax-detection heuristic reparsed those files as ESM mid-`require()`. The gulpfiles that load them now use `await import("./server.js")` instead of `require("./server")`.
- `node-config` was upgraded to `config@^5.0.0-alpha.2`, which ships a genuine ESM entry point (`config/lib/config.mjs`) alongside its original CJS entry. Every file under `config/` (`default.cjs`, `local.cjs`, `config/me/**`) was renamed from `.js` to `.cjs`, since config's real ESM entry loads these data files based on the nearest `package.json`'s `"type"` field (the repo root's `"type": "module"`), and a bare `.js` file there would be misparsed as ESM despite its actual `module.exports` content. Genuine non-bundled ESM call sites (`buildPugLocals.js`, and `packages/service`'s config loader) import the explicit subpath `config/lib/config.mjs`, since `config@5.0.0-alpha.2` doesn't declare an `"exports"` map yet; `require()`-based call sites (gulpfiles/`server.js` files using `createRequire`) and webpack-bundled contexts correctly keep resolving the bare `"config"` specifier to its CJS/`"module"` field respectively, and don't need the subpath.
- Two more instances of the same old node-config "computed property" convention (`function () { return this.foo.bar; }`, relying on function-valued config entries being auto-evaluated as getters - a behavior the installed `config` version no longer provides) were found and fixed in `config/me/organizations/me.js`/`config/me/persons/me/index.js` (contact info) and `config/default.cjs` (`resume`/`letter`/`www`'s service-worker bundle names) - all were self-referential to values already present in the same object, so they were replaced with static equivalents.
- `packages/service`'s ~150 source/test files, `gulpfile.js`, and `webpack.serverless.config.js` were all converted from CommonJS to genuine `import`/`export` syntax. Its `mocha.config.js` was renamed to `mocha.config.cjs` (Mocha's own config loader needs synchronous CJS, matching every other package's convention), and its config loader (`src/serverless/util/loadConfig.js`) was kept CommonJS and renamed to `loadConfig.cjs`, since it's invoked directly by the Serverless Framework's own `${file(...)}` variable-resolution syntax in `serverless.yml`/`env.yml` - a mechanism that loads referenced scripts via a synchronous internal `require()`, not `import()`.
- The old `freshRequire` test helper (which cleared `require.cache` and reloaded modules as a stubbing substitute) fundamentally didn't work once `packages/service` became real ESM - Node caches native ESM module instances internally with no public API to bust that cache, so stubs silently stopped applying. It's been replaced with `esmock` (a purpose-built ESM module-mocking library) across all 15 former callers, and the helper itself has been deleted. One known exception: `esmock` can't intercept `@randy.tarampi/serverless`'s doubly-nested dynamic re-export pattern in its built `es5/index.js` output (Node's own native interop handles it fine, but `esmock`'s static analysis can't), so the handful of tests that needed to mock its `responseBuilder` were rewritten to exercise the real function's computed output instead - not a weakened test, but worth knowing if that package's build output shape ever needs to change.
- **Fixed regression - `www` dev-server `react-router` crash, and `reactRouter.cjs` removed entirely:** `packages/jsx/src/lib/reactRouter.cjs` used to be the last CJS wrapper in the otherwise all-ESM `jsx` package - a `require.resolve("react-router/package.json")` + dynamic-require hack reaching directly into `react-router`'s installed `dist/{development,production}/lib/*.js` files, originally added (commit `1ce4d7300`) to work around `require("react-router")` crashing Mocha with `ERR_REQUIRE_ESM` (since `react-router` itself is `"type": "module"`). This hack could never work in a real browser bundle: there is no `require`/`require.resolve` at runtime in a browser, so `__non_webpack_require__` (its own fallback) was also undefined there, and webpack's static analyzer flagged the dynamically-computed `require()` call as a "critical dependency", replacing it with a stub that throws `Cannot find module '<path>'` - reproduced exactly as the reported `www` dev-server browser crash (`Cannot find module 'react-router/package.json'`). Verified the original blocker is gone: this repo's Node runtime (v24) now supports synchronously `require()`-ing a genuine ES module without error, and `react-router@8.0.1`'s main entry already exports everything the wrapper was manually re-implementing (`Router`, `Route`, `Routes`, `StaticRouter`, `matchPath`, `useLocation`, `useParams`). Fixed by deleting `reactRouter.cjs` entirely and switching its 6 first-party consumers to a plain `import {...} from "react-router";`, and removing the now-unneeded `react-router` exclusion from `babel.register.cjs`'s `only` regex (it existed solely to let the old hack's dynamic requires into `react-router`'s dist files be transformed at test time).
- `materialize-css` and `react-materialize` are legacy but still functional.
- `packages/jsonresume-theme/webpack.publish.config.js` uses `output.libraryTarget: "commonjs"` (not the base config's usual `"commonjs2"`) and disables `webpack-node-externals`' auto-detection for `query-string` (declared explicitly external instead). This bundle has exactly one first-party module and nothing else requiring it, so webpack inlines the entry module directly instead of wrapping it in the normal `(module, exports, require) => {...}` factory; with `"commonjs2"` this silently discarded every export via a stray `module.exports = <unrelated helper var>` at the end of the bundle. If this bundle ever gains a second internal module (so webpack no longer takes the single-module inlining path), it's worth re-checking whether `"commonjs2"` works correctly again.
- `@randy.tarampi/redux-metrics`'s `test` task is intermittently flaky: `gulp.parallel(["test.unit", "test.integration"])` (in `gulpfile.base.js`'s shared `test` task) occasionally fails when both run concurrently, even completely outside of Nx/lerna (reproduced with a bare `gulp test` run 3 times in a row: pass, fail, pass), while `test.unit` alone is always reliable. This is pre-existing flakiness, not a regression from the `build`/`test`/`job-applications` fixes; it needs its own root-cause investigation (likely a race in how the two mocha subprocesses start up in parallel).
- `resume`/`letter`/`www`'s webpack client entries reference `raf/polyfill` (for `materialize-css`) but never declared `raf` as an explicit dependency of their own - it only worked previously via accidental hoisting from `enzyme`'s own transitive dependency. Now that the unused `enzyme`/`chai-enzyme` devDependencies have been removed from `packages/printables` and `packages/job-application` (confirmed zero usages), `raf` is declared explicitly in `resume`/`letter`/`www` instead.
- `packages/printables`'s `renderPdf`/`renderPrintablesToHtml` now create their destination directory (`fs.promises.mkdir(printableDestinationDirectory, {recursive: true})`) before writing any output - Puppeteer's `page.pdf()` and `fs.writeFile` never created missing parent directories on their own. This was previously masked for `letter`/`resume`/`jsonresume-theme` because their own `build` step happened to create `dist/` as a side effect (webpack bundling, or an explicit `mkdir -p dist`), but `packages/job-application` has no build step that creates `dist/` - only a one-time `postinstall: mkdir -p dist` - so `yarn lerna run clean` followed by `yarn lerna run job-applications` used to crash with `ENOENT` on a fresh/cleaned tree. This class of "missing output directory" bug is now fixed once, at the shared `printables` library layer, for all current and future consumers, rather than relying on any single package's build side effects.
- **Fixed - `config/production.yml` doesn't exist gotcha:** `config/` has no `production.yml`/`production.cjs` - only `dev.yml`, `prd.yml`, `test.yml`, and `printable.yml` (plus `default.cjs`/`local.cjs`) exist. Per `node-config`'s own resolution convention, a bare `NODE_ENV=production` used to mean only `default.cjs` + `local.cjs` were loaded, silently skipping every `dev`/`prd`-specific override (`www.assetUrl`, `sentry.dsn`, `gtm.container.id`, `ga.property.id`, etc.) and printing a `WARNING: NODE_ENV value of 'production' did not match any deployment config file names.` on every `build`/`job-applications` run. Rather than pairing `NODE_ENV=production` with an explicit `NODE_CONFIG_ENV=prd` in every build script (which assumed every build is "production-bound" in intent, which isn't actually true - a build triggered as an Nx dependency of `test`, or a standalone rebuild, isn't necessarily meant to be one), library packages' `build`/`build:babel:esm`/`build:gulp` scripts no longer hardcode either variable at all - they now simply inherit whatever the caller already has. `babel.config.js` sets `process.env.NODE_CONFIG_ENV = process.env.NODE_CONFIG_ENV || process.env.NODE_ENV || "prd"` before requiring `config`, mirroring `config`'s own `NODE_CONFIG_ENV`-falls-back-to-`NODE_ENV` chain but replacing its ultimate `"development"` default (which doesn't match any file here either) with `"prd"` - so a caller that already sets a real `NODE_ENV` (`test`, `development`, `printable`) is respected untouched, and only a truly bare invocation safely defaults to `prd`-flavoured config instead of warning or baking in the wrong values.
- **Fixed - `packages/views/gulpfile.js` missing `NODE_CONFIG_DIR`:** unlike every sibling gulpfile (`job-application`, `jsonresume-theme`, `letter`, `resume`), `packages/views/gulpfile.js` never set `process.env.NODE_CONFIG_DIR` before its `views:index` task's `buildPugLocals()` call requires `config` - so `config` fell back to its own default directory resolution, found no config sources at all, and printed the same `NODE_ENV value of '...' did not match any deployment config file names.` warning regardless of what `NODE_ENV`/`NODE_CONFIG_ENV` were actually set to. This was the real, concrete source of the originally-reported warning (not merely a `NODE_ENV`/`NODE_CONFIG_ENV` decoupling gap) - fixed by adding the same `NODE_CONFIG_DIR` assignment already used by its sibling gulpfiles.
- **Fixed regression - blank PDF content:** commit `b2f75d80f` ("phase 2+3 - known hacks resolved + CJS→ESM migration") accidentally created stub files `packages/resume/src/public/views/serverApp.js` and `packages/letter/src/public/views/serverApp.js` (rendering only the person's name) alongside the real, fully-featured `serverApp.jsx` components, then blindly appended `.js` to `index.server.js`'s export specifier and left `gulpfile.js`/`renderHtml.js`'s extensionless/wrong-extension requires to resolve to the stub instead of the real component - silently shadowing the actual resume/letter content in every generated PDF/HTML. The integration tests never caught this because they imported `serverApp.jsx` by its exact, explicit filename, bypassing the ambiguous resolution the real production path used. Fixed by deleting both stub files and pointing every call site (`index.server.js`, `gulpfile.js`, `renderHtml.js`, for both `resume` and `letter`) at the real `serverApp.jsx` explicitly.
- **Fixed regression - `www` dev-server ESM crash:** the `www` package's dev-server bundle (`yarn run start:www`/`dev:client`) crashed in a real browser with `ReferenceError: exports is not defined` for both the main app bundle and the service-worker installer bundle. Root cause: `ReactRefreshWebpackPlugin` (only active when `NODE_ENV=development`) injects a real-ES-module preamble into every Babel-processed module, but `babel.config.js`'s `client.esm` case was transpiling those same modules to CommonJS (`modules: "commonjs"`) - webpack then wrapped them with its own ESM-style `__webpack_exports__` parameter while the module body still referenced the bare `exports` identifier, which didn't exist in scope. Fixed by giving `packages/www`'s own webpack ESM bundle a dedicated Babel env (`client.esm.webpack`, set only in `webpack.client.config.esm.js`) with `modules: false`, so Babel preserves real ES module syntax there - critically, this had to be a **new, separate** env name rather than repurposing `client.esm` itself, since `client.esm` is also used by every other package's own `build:babel:esm` library-transpile script (which needs `modules: "commonjs"` for its `esm/` output directory, explicitly declared `"type": "commonjs"` via its own `esm/package.json"`) - reusing `client.esm` for both purposes broke those 12 packages' library builds (surfaced as `jsonresume-theme-randytarampi:test` failing to load `browser-logger`'s `esm/index.js`). Preserving real ESM syntax also triggered Node's strict "fully specified" import-specifier resolution for bare/extensionless imports inside `"type": "module"` packages pulled into the bundle (e.g. `lodash/isFunction` from `@randy.tarampi/jsx`'s source) - fixed by adding `resolve: {fullySpecified: false}` to the shared babel-loader rule in `webpack.client.config.base.js`.
- **Delivered - automated console-error smoke test:** the earlier follow-up recommendation to add "a Puppeteer-based console-error smoke test" for the `www` dev bundle is now delivered: `packages/www/test/integration/dist/browserBundle.js` boots a local static server for `packages/www/dist`, loads the built ESM bundle in a real headless Chromium instance via Puppeteer, and asserts zero uncaught runtime errors plus real rendered content, as part of `yarn lerna run test --scope=@randy.tarampi/www` - closing the gap where every one of the last several `www` dev-server regressions could only ever be caught by a human opening a real browser. (This test originally used `jsdom`, relying on it skipping `<script type="module">` tags and falling back to a `nomodule`/ES5 sibling bundle; once the ES5 web build was dropped in favour of shipping ESM only, that fallback no longer existed, so the test was rewritten to use Puppeteer, which actually executes `type="module"` scripts.) The other half of that same recommendation - a lint/CI check against a bare `.js` file silently shadowing a same-named `.jsx` sibling - remains a documented, not-yet-delivered follow-up.
- **Fixed regression - `www` dev-server `immutable` interop crash:** after the previous two `www` dev-server regressions were fixed, the bundle progressed further and hit a third, previously-unreached crash: `TypeError: undefined is not an object (evaluating 'immutable...["default"].Iterable')` inside `packages/jsx/src/lib/reactShim.js`. Root cause: `reactShim.js` used a default import (`import Immutable from "immutable";`), but `immutable@5`'s `package.json` declares no `"exports"`/`"browser"` field, so webpack's `target: "web"` `resolve.mainFields` (`["browser", "module", "main"]`) resolves the bare `"immutable"` specifier to its real-ESM `dist/immutable.es.js` build - which has no `export default` at all (only named exports). A default import against a module with no default export resolves to `undefined` under real ESM interop, so every property access on it (`Immutable.Iterable`) crashed. This precondition wasn't new - it predates this session's Phase 6 work - but was never reached until the earlier two crashes blocking evaluation of this module were fixed first. Fixed by changing the import to a namespace import (`import * as Immutable from "immutable";`), mirroring the already-working pattern in this same package's `src/lib/store/configureStore.js`; a namespace import always exposes every named export as a plain property regardless of which build (CJS `main` or ESM `module`) webpack picks, so it's correct either way.
- **Fixed regression - `www` dev-server `redux-immutable` interop crash:** a fifth, still-deeper crash surfaced once the `immutable` fix above let the bundle progress further: `TypeError: undefined is not an object (evaluating '_immutable2.default.Map')` inside `configureOfflineStore`. Root cause: the same `immutable@5` real-ESM-resolution behavior as above, but this time inside **third-party, unmodifiable** `node_modules` code - `redux-immutable`'s own pre-compiled `dist/combineReducers.js`/`dist/utilities/getUnexpectedInvocationParameterMessage.js` do `_interopRequireDefault(require('immutable')).default.Map`, a shape that only works against a CJS/UMD build. Since a source-level namespace-import fix (the Phase 7 approach) isn't available for third-party compiled code, fixed instead by adding `"immutable$": require.resolve("immutable")` to the shared `webpack.client.config.base.js`'s `resolve.alias`, forcing every consumer in the bundle - ours and `redux-immutable`'s alike - to resolve `"immutable"` to its CJS/UMD build, mirroring what `webpack.publish.config.base.js`'s `mainFields: ["main", "module"]` already did for the PDF-generation path (which is why this bug was never reported from there). Verified via a red/green check: the new `packages/www/test/integration/dist/browserBundle.js` smoke test (see above) fails without the alias and passes with it.
- **New, pre-existing, out-of-scope bug found while building the `browserBundle.js` smoke test:** `packages/jsx/src/lib/middleware/ui.js`'s swipeable-tabs index-computation logic has a real race, unrelated to any of this session's changes (confirmed via `git blame` to predate this whole engagement): on the very first `LOCATION_CHANGE` action - dispatched by `redux-first-history` synchronously at store creation, before this app's own `SET_ROUTES` action has been dispatched (which only happens once `redux-offline`'s async rehydration completes) - `getIndexForRoute` legitimately returns `null` (no indexed routes yet), and indexing `swipeableTabs.$tabLinks[null]` is `undefined`, crashing on `.hash`. The new smoke test tolerates this one specific, already-diagnosed error signature (documented inline in the test) rather than silently hiding it, so it doesn't mask this class of bug for anything else; fixing it is out of scope for this plan and left as a follow-up.

## Recommended next modernization phase

Now that `build`/`test`/`job-applications` are fixed at the source (not just patched around in CI), the next steps in the same direction:

- Continue executing `docs/MATERIALIZE_MIGRATION.md`'s phased replacement of `react-materialize` (peer deps on React `^17` only) - the actual source of the remaining React-peer-range warnings; a React version change would not have resolved this, since it doesn't support React 18 either. (`react-google-maps` was already fully replaced with `@vis.gl/react-google-maps` in an earlier session, so that half of this bullet is done.)
- `chai`, `gulp-mocha`, and `webpack-cli` are all current (`^6.2.2`, `^10.0.1`, `^7.2.1` respectively); `chai-dom` (an unused `packages/jsx` devDependency) was dropped entirely. `webpack-dev-server` was deliberately held back at `^5.2.6` (not bumped to `^6.0.0`): `@pmmmwh/react-refresh-webpack-plugin` (used for React Fast Refresh in `letter`/`resume`/`www`'s dev servers) statically imports a `webpack-dev-server` SockJS client export removed in v6, and its latest published release (`0.6.2`) still only declares peer-dependency support for `webpack-dev-server` `4.8.0+`/`5.x` - revisit this once that plugin ships v6 support.
- `unsplash-js@^7` (used in `packages/service`) is one major behind; `v8` is a full TypeScript rewrite with a different response shape (`{data, error}` instead of the `{response}` this repo's `UnsplashSource` currently destructures) per its own changelog. Deliberately deferred given the low usage surface (one file, one `createApi` call) but genuinely high rewrite risk.

## `packages/jsx/src/lib/reactShim.js`

This shim exists to keep React 19 working with a few legacy dependencies.

- `global.IS_REACT_ACT_ENVIRONMENT`
  - Why: React Testing Library expects it to exist before tests start; we set it in the test bootstrap so mocha leak checks treat it as baseline state.
  - Remove when: the test setup no longer needs the global (or React/RTL provide it automatically).

- `ReactDOM.findDOMNode`
  - Why: legacy DOM-driven UI deps in this package still rely on it (`react-materialize` / swipeable tab helpers).
  - Remove when: those dependencies are upgraded or replaced so they use refs instead of `findDOMNode`.

- Immutable legacy statics (`Iterable.isIterable`, `isKeyed`, `isIndexed`, `isAssociative`, `isOrdered`)
  - Why: `@actra-development-oss/redux-persist-transform-filter-immutable` still calls the pre-v5 Immutable statics.
  - Remove when: that dependency is upgraded or replaced and no longer needs the legacy `Immutable.Iterable.*` helpers.
